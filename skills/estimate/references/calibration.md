  → **驗證基礎設施從「新建 1–2 hr」降為「擴充 0.5 hr」**。估新功能時不要再算全額

### RWD

> ⚠️ **2026-08-03 更正：這條原本寫「桌機專用，不做 RWD，估時不用算」，已被需求方推翻。**
> Lend Zone 專區實作到一半時 KuanLin 主動指出「你要考慮 RWD 喔！不一定都是桌機」。
> **「repo 現況沒有 media query」不等於「需求方不要 RWD」** —— 前者是現狀，後者是需求。這是兩件事，必須直接問。

現況：全 repo 僅 1 個 media query（`src/sass/base/_typography.scss:713`，`max-width: 900px`，只服務 `.scodeFilter`）。`public/index.html:6` **有** `viewport` meta，所以行動裝置會用實際寬度渲染。

**估時要算，而且要分兩層報價：**

| 層級 | 內容 | 成本 |
|---|---|---|
| **平板可用（≥768px）** | 自己功能內的 grid / toolbar / 查詢區收斂 | **約 1–1.5 hr**，且必須跨寬度實測 |
| **手機可用（≤430px）** | **卡在全站共通的 `Navbar`**：側欄固定 190px 無收合，700px 以下內容區只剩 ~60px，**既有頁面同樣不可用**（已用 `DayTradingBuyback` / `InsufficientFunds` 對照驗證） | 改 `Navbar` + `_nav.scss`，影響 200+ 頁面 → **獨立專案，不要吃進單一功能的估時** |

**RWD 的兩個踩雷點（寫死在這裡，下次直接避開）**：

1. **grid 軌道不要用 `minmax(240px, 1fr)`** —— 會強迫軌道至少 240px，容器裝不下就把整頁撐出橫向捲動。4 欄卡片實測把頁面撐到 1304px，**連 1280 的筆電都中**。改用 `minmax(0, 1fr)` + 斷點決定欄數，或 `minmax(min(240px, 100%), 1fr)`。
2. **長文字列不要整列 `white-space: nowrap`** —— 名單頁 toolbar 的「※每日初始檔案於13:00產出 資料更新時間：…」把 768px 視窗撐到 886px。只讓不該斷的片段 nowrap。
3. flex/grid 子項補 `min-width: 0`，否則預設 `min-width:auto` 會擋住收縮、把寬度往外傳。

**驗證方式**：用 Playwright 量 `document.documentElement.scrollWidth > window.innerWidth`，跨 768/1024/1280/1920 跑。**不要只看截圖** —— 單一寬度（尤其 1600px）驗不出這類 bug。

### 新的教訓

1. **抓 demo 站要先看原始碼形態。** 一個 `curl` + `grep '<script'` 就能知道是編譯過的 bundle 還是內嵌 JSX。這個動作值 6 hr 以上，而且會連帶消掉「上百處顯示決策」的整條風險。**下次估時的第一個動作**。
2. **「建置佔比」要重新定錨。** 本案實測建置佔總成本約 7%（scenario A）而非估的 47%。金融 CMS 的 46% 參考值是**人類逐行 review 前提下**的數字；改用機器驗證後，建置佔比會塌到 10% 以下，剩下的全是 ④⑤ 與 review 決策。
3. **「人類 review 要不要做」是估時最大的單一分岔**，比 API 完整度更大。7,266 行沒人讀 → 若團隊要求 merge 前人工 review，那 25 hr 一分都省不掉；若接受「測試 + 程式化量測 + UAT」當關卡，只需針對金額計算與 rules 模組抽查約 3 hr。**這一條必須在估時階段就問，並綁成前提。**
4. **平行 agent 的上限不是「review queue」，是「共寫點」。** 估時寫「甜蜜點 3–4 個」的理由是人類 review 塞車；實際塞車點是**兩個 agent 對同一支 endpoint 各自發明註冊機制**而互相覆蓋（每日通知控管 T日/T+1/T+2 共用一支 API）。派工時「唯一共寫點」不只要標出來，**必須連機制一起指定**，否則等於邀請每個人各寫一套。

### 教訓（下次估時要帶走的）

1. **一定要問 RWD** —— 對方第一個問的就是這個，而我漏了。查證後答案是「不用做」，但沒查證前無法回答，就顯得估時不紮實。

## 4. 案例：新手測驗（Rookie Test）四系統

| 項目 | 內容 |
|---|---|
| 估時日期 | 2026-08-06 |
| 規格 | `admin-frontend/rookie-test-flow.html`（54.7 KB、`<script>` **0 個** → 手寫靜態 HTML，版面與文案全內嵌）；上游另有「規格卡片 v3」未取得 |
| 範圍 | CMS 前端 + CMS 後端 + SSO + FastPxy。**排除 App**（iOS/Android 另組） |
| 條件 | 全 AI 開發、人類輔助、含測試、多 agent 平行、**報淨值不抓 buffer** |
| **定案（v4）** | **32.5 hr capacity**（我的淨工時 22.9 + 等他人 9.5）= **5.5 個工作日 @ 6 hr/天** |
| 實際工時 | **尚未開工**（估時階段，需求仍有 3 個未定項）|

### 需求形態

固定 5 題單選測驗，攔 B27=0 的新手；CMS 維護題庫並留紀錄；SSO 依機率分類並發旗標；App 透過 FastPxy 拿題目，不用就回空。

### 四版修正歷程與**單一根因**

| 版本 | 數字 | 變動原因 | 方向 |
|---|---|---|---|
| v1 | 62.5 | 首估，FastPxy 當成有邏輯的聚合層 | — |
| v2 | 54.0 | 需求方指出 FastPxy 是 bypass → 聚合／快取／錯誤語意搬到 SSO/CMS/App | ↓ 8.5 |
| v3 | 43.0 | 改用迴圈模型（D/J 分開計價）；`need_rookie_test` 證實是既有 flag 機制擴充 | ↓ 11.0 |
| **v4** | **32.5** | **SSO 是 additive 不是改造**（12.5 → 4.3）＋ 拔掉三格 padding | ↓ 10.5 |

> **四版全部往下，根因只有一個：只要「動到別人的系統」就套改造既有溢價。**
> 這個病徵（連續單向修正）比「在同一數字附近打轉」更危險，因為它看起來像在收斂。
> **處置是停下來命名根因並一次修完**，而不是等對方每質疑一格就讓一格。
> 防護：主動標出**唯一往上的那一格**（本案是 SSO 回歸 1.5 → 2.0，理由是動正式機旗標邏輯）。若連一格都往上不了 = 還沒找到根因。

### 新教訓（優先於Lend Zone 案的教訓）

1. **additive vs 真改造是最大的單一價差。** 判準：「舊 client 打同一支 API，行為會不會變？」不會 → additive，按新增碼定價、回歸不含既有路徑、review 不逐行。誤判一格 8 hr，四格 30 hr。
2. **Step 0.5「這件事現在是怎麼做的？」比驗 demo 形態更高投報率。** 需求方一句「`can_online_happy_call` 已經有了」讓 App 端從 15~20 hr 塌到「多一個 else if」。**要問到具體欄位名，然後 grep。**
3. **需求方口述 > 規格文件。** 本案兩處重大分岔：規格寫「進下單匣前攔 6 個入口」需求方說「登入後拿一次」（App 差 15~20 hr）；規格是「測驗」需求方三次寫「問券」（差 8~12 hr）。**口述與文件不一致時逐條對帳，差異就是最大的成本分岔。**
4. **校準數字必須按量體外推。** 「無 TS 靜默失敗 3 次」是 7,266 行/12 單位的實測；套到 2,500 行/6 單位應該是 1.5 次。**照抄校準數字就是抓 buffer。**
5. **同名代號不同義要對死。** `B27` 在 CMS 是聯徵「開戶戶數」風險因子（`AMLReviewRiskPage.mock.js:132`），在規格書裡是「首次開戶分眾」。工程師 grep 會查到錯的東西。
6. **多系統需求的成本在邊界**：同一契約對 N 方、**N 條發版 pipeline 不可合併**、一個語意（fail-open／逾時／錯誤碼）在 N 層各實作一次。但**不要因此把每個系統都當改造**——先過 additive 判準再加邊界成本。
7. **報淨值。** 需求方明確指定「一天 6 hr 已含 buffer，不用再抓」。取代 buffer 的是「破了會漲的具名前提」，把風險連同觸發條件交還對方。
