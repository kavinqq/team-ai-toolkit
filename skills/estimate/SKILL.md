# AI 時代的工時估算

## 為什麼需要新方法

傳統估時 = 程式碼量 × 加速比。**這在 AI 開發下已經失效**，因為程式碼產出已不是瓶頸。

新的成本結構：把工作分成五桶 + 一個獨立計價的 review 桶。

| 桶 | 內容 | AI 可加速 |
|---|---|---|
| **① 前置** | 規格轉譯：把 PM 文字/Figma/demo 轉成 AI 可執行的欄位表、互動規則、API 契約 | **視 demo 形態而定，可能歸零**（見 Step 0） |
| **② 建置** | 派工 + 與 AI 來回對到跑得起來 | **極高**（實測已塌到總成本 10% 以下） |
| **③ 卡關** | 已知會多輪的難點（AI 看不到結果、**真**改造既有邏輯、無型別安全網） | 中（省思考、不省輪次） |
| **④ 經驗調整** | 對版、與既有頁面一致性、空狀態、文案語氣 | **接近零**（AI 沒有眼睛） |
| **⑤ 收尾** | 串真實 API、UAT 輪次、回歸、MR、發版 | **零**（受他人節奏綁定） |
| **⑥ Review** | 人類讀 AI 產出的程式碼 | **零，但深度可選** —— 這是估時最大的單一分岔，見 Step 6 |

> **⚠️ 2026-08 實測校準：桶②不再是主要成本。**
> Lend Zone 專區實測（`references/calibration.md` §3）：桶①②③ 原估 48 hr，實際 1.75 hr wall clock。
> **建置佔比從 47% 塌到 7%。** 現在決定總價的是 ⑥ review 深度 與 ④⑤ 這些「他人時間 / AI 沒有眼睛」的桶。

**估時要先問的三句話（依序）：**

1. **「這件事現在是怎麼做的？有沒有既有的 flag / 欄位 / API？」**（Step 0.5）—— 一個既有欄位名可以讓整格成本崩塌
2. **「review 要做到多深？」**（Step 6 前提 1）—— 值 3~25 hr
3. **「這是 additive 還是真改造？」**（Step 3）—— 誤判會高估 3 倍

「這個案子多大？」已經幾乎不影響數字 —— 實測 production 行數預測準（+13%），但工時差 27 倍。<br>
「建置佔比多少」也不再是主要問題，見文末〈建置佔比的參考值〉。

## 工作流程

### Step 0 — 先驗 demo / prototype 的原始碼形態

**在讀規格之前先做這件事**（但 Step 0.5 的那個問題投報率更高，兩件都要做）。 一個 prototype 站可能是編譯過的 bundle，也可能把未編譯的原始碼整包內嵌 —— 兩者對桶①的價差是 **6 hr 以上**，還會連帶決定「規格未涵蓋的顯示決策」這條風險存不存在。

```bash
curl -sL <demo_url> -o demo.html
wc -c demo.html                                    # 單檔 300KB+ 且沒有外部 JS → 高度可疑是內嵌原始碼
grep -oE '(src|href)="[^"]*\.js"' demo.html        # 只有 react/babel CDN → 原始碼就在檔案裡
grep -n '<script' demo.html                        # 找 type="text/babel" / type="module"
```

**判定與定價：**

| demo 形態 | 徵兆 | 桶① 成本 | 「上百處顯示決策」風險 |
|---|---|---|---|
| **內嵌未編譯原始碼** | 單檔大、只載 CDN 的 react + `@babel/standalone`、有 `<script type="text/babel">` | **≈ 20 min**（抽出來就是規格） | **歸零** —— 欄位順序、文案、算式全都在 |
| 編譯過的 bundle | 有 `main.<hash>.js`、程式碼 minified | 3–6 hr（要靠畫面推欄位） | 高，照原本估 |
| 靜態截圖 / Figma only | 無 JS | 6 hr+ | **最高**，且 Figma 常需登入而拿不到 |

若是內嵌原始碼，直接把 `<script>` 區塊拆出來當**唯一視覺真相**，逐字抄文案與算式。實測這一步讓「規格未涵蓋的顯示決策約上百處」整條風險消失。

> **「抓不到渲染後的 DOM」不等於「拿不到原始碼」。**(Lend Zone 案,見 calibration.md §3)

### Step 0.5 — 問需求方「這件事現在是怎麼做的？」（**最高投報率的單一問題**）

規格文件會描述「要做什麼」，但幾乎不會寫「現在已經有什麼」。而後者決定成本。

**要問的具體形式**（不要問抽象的「有沒有類似功能」，要問可以 grep 的東西）：

> 「這個判斷現在有沒有既有的 flag／欄位／API？叫什麼名字？」
> 「現在同一群使用者是怎麼被處理的？誰決定的？存在哪？」
> 「App／前端現在有沒有一個地方在讀這類旗標並分流？」

**為什麼是最高投報率**：2026-08 新手測驗案，需求方一句「`can_online_happy_call` 已經有了，只是想個辦法讓他有另一個 flag」，讓
- App 端從「收斂 6 個下單入口、15~20 hr」→「多一個 else if」
- SSO 從「新建分類系統 12.5 hr」→「既有 API 多回一個欄位 4.3 hr」

**拿到欄位名後立刻 grep 全 repo**，並注意**同名不同義**：
```bash
grep -rni "<既有欄位名>" src | head -20     # 找既有的產生點與消費點
```
> 同一代號可能兩種含義(例 `B27`,見 calibration.md),**代號一定要跟需求方對死語意。**

**需求方用自己的話重述需求時，逐條與規格文件對帳。** 差異就是最大的成本分岔，而且**口述優先於文件**（文件常是舊版或原型作者的想像）。2026-08 實測到的兩個分岔：

| 規格文件說 | 需求方口述說 | 價差 |
|---|---|---|
| 進下單匣前攔截，觸發點 6 個 | 登入後拿一次，回空就沒事 | App **15~20 hr** |
| 測驗（有正解、全對才過） | 「問券」 | App **8~12 hr** |

### Step 1 — 先勘查 repo，不要憑印象估

**在寫任何數字之前**，把以下事實查出來並附 `檔案:行號`。每一條都要能被別人打開驗證。

```bash
# 技術棧與規模
cat package.json | head -60
find src -name "*.js" ! -name "*.test.js" ! -path "*__mock*" | wc -l
find src -name "*.test.js" | wc -l          # 測試慣例 = 固定成本，不能省

# 有沒有型別安全網？（決定 ③ 卡關桶的大小）
ls tsconfig.json 2>/dev/null || echo "無 TypeScript → prop 傳錯不報錯，只能人眼抓"

# RWD 要做到什麼程度？（最常被漏問的一項）
grep -rn "@media" src/sass/ src/styles/ 2>/dev/null | wc -l
grep -n viewport public/index.html
# ⚠️ 「repo 現況沒有 media query」不等於「需求方不要 RWD」。這是現狀 vs 需求，必須直接問。
# 要分兩層報價：平板可用(≥768px) 約 1–1.5 hr；手機可用通常卡在全站共通的側欄，屬獨立專案。
# 側欄寬度實測：grep 側欄 class 的 width，再算「視窗 − 側欄」剩多少給內容區。

# 需要的元件到底存不存在？（不要假設「UI lib 應該都有」）
grep -n "^export \(function\|const\)" src/components/HTMLElement.js   # 或對應的元件庫入口

# 同類功能是否已有既有實作？（改造 vs 新建，價差很大）
grep -rn "<關鍵字>" src/utils/navData.js src/utils/navDataIndex.js

# 歷史交付規模基準（校準用）
git log --since="6 months ago" --pretty=format:"%h|%ad|%s" --date=short --shortstat | grep -B1 "files changed"
```

**Step 1 的產出是一份「可驗證事實清單」。** 這是後續所有爭論的共同地基——沒有它，估時討論會變成兩個人各說各話。

### Step 2 — 數「畫面單位」，不要數「頁面」

規格寫「6 個頁面」不代表 6 個畫面單位。判準：

> **一個彈窗如果自己就含「查詢條件 + 表格 + 勾選 + 操作按鈕」，它就是一個獨立畫面單位，不是附屬 modal。**

實例：規格 6 頁 → 實際 12 個畫面單位（3 個「彈窗」各自是完整的查詢+表格+匯出+批次操作畫面）。**這是估時被低估最常見的單一原因。**

### Step 3 — 建置桶用「團隊實測速度」，且必須分級定價

- **一定要問實測速度**：「你現在跟 AI 來回對，一個 page 大概多久？」通用係數永遠不如團隊自己的數字。
- **絕對不要均一價。** 這是最容易犯的懶惰錯誤。分三級：

| 級別 | 型態 | 相對價 |
|---|---|---|
| 簡單 | 純表格 + 基本查詢、單純確認視窗 | 0.4× 實測速度 |
| 中等 | 欄位多但機械（15–20 欄）、資訊展示彈窗 | 0.6–0.7× |
| 複雜 | 多欄位表單 + 驗證、動態增刪列、**改造既有程式碼** | 0.9–1.0× |

> 「18 欄表格」在 AI 開發下**幾乎不比 6 欄貴**（AI 產出同樣快、人也只掃一次欄位表）。**欄位數不再是成本驅動因子，互動複雜度才是。**

#### 「改造既有」的溢價判準：additive 還是真改造？

**「改造既有比新建貴」是對的，但判準不是「有沒有動到別人的系統」，而是「有沒有改變既有路徑的行為」。**
這是 2026-08 新手測驗案的系統性錯誤來源 —— 四輪估時單向下滑 30 hr，全部來自這一條誤判。

| 型態 | 特徵 | 定價 | 回歸範圍 | Review |
|---|---|---|---|---|
| **Additive**（加法） | 加欄位／加 flag／既有 API response 多回一個值／在既有分歧點加一個**獨立**分支／新增一支 endpoint | **按新增碼定價，無溢價** | **不含既有路徑** —— 跑既有測試 + 冒煙一次即可 | 按新增行數，不必逐行 |
| **真改造** | 改既有判斷條件／改既有欄位語意／重寫狀態機／既有流程的順序或結果會變 | **0.9–1.0× 且必然多輪** | **必須涵蓋既有路徑全部情境** | 被改動的區塊逐行 |

**判準的操作方式**：問「**這次改動之後，一個完全沒升版的舊 client 打同一支 API，行為會不一樣嗎？**」
- 不會 → additive
- 會 → 真改造，溢價成立

**Additive 常被誤判成改造的三個場景**（看到就套上表左欄）：
1. 在別人的系統加一個欄位並在既有 response 帶出去
2. 在既有的 flag 分流點加一個優先分支，而**優先序判斷做在 consumer 端**（consumer 沒改到既有分支）
3. 新增一支獨立 endpoint，不碰既有 endpoint

> 真改造的症狀是「行為變怪」而非拋錯，只有人點得出來 —— **這句話只適用於真改造那一欄。** 套到 additive 上就是在賣空氣。

### Step 3.5 — **用「迴圈」計價，且迴圈不是均一價**（全 AI 開發下的正式計價單位）

全 AI 開發的實際工作單位不是「小時」，是**下 prompt → 等 → 看結果**的迴圈。用小時估會系統性高估，因為「等」的時間人類不在場。

**迴圈分兩型，人類成本差 5 倍：**

| 型態 | 內容 | 人類注意力/迴圈 | wall clock/迴圈 |
|---|---|---|---|
| **派工型 D** | 大 prompt 丟出去、agent 自己跑測試、人只看綠燈與 diff 摘要 | **~4 min** | 15–25 min（可平行） |
| **判斷型 J** | debug 行為變怪、對版、整合衝突、真改造既有邏輯、跨寬度看溢出、規格轉譯與派工撰寫 | **~20 min** | 20–40 min（不可平行） |

**不算迴圈的純人類工時**（不可用迴圈換算，AI 幫不上）：架構 review、UAT 對應、回歸、發版。

**計算式：**
```
迴圈人類工時 = D 迴圈數 × 4 min + J 迴圈數 × 20 min
建置 wall clock = D 迴圈數 × 20 min ÷ 平行 agent 數
我的工時       = 迴圈人類工時 + 純人類工時（review / 聯調 / 回歸 / 發版）
```

**怎麼數迴圈**：一個畫面單位或一支 API 群 = 1–3 個 D（首發 + 修正）；每一條**已查證的**卡關項 = 1–3 個 J。
派工 prompt 的撰寫本身算 J（人要寫範圍、附 golden reference、指定共寫點機制）。

**校準基準**（`references/calibration.md`）：Lend Zone 專區 5 agent、桶①②③ wall clock 1.75 hr、人類注意力 20 min —— 換算約 12 D + 1 J。這個比例只在「驗證交給測試、人只看綠燈」時成立；一旦進入 debug／對版就是 J。

> **迴圈模型與法 A（畫面單位 × 實測速度）的關係**：法 A 適合對外報價與跨人對帳（大家都懂「一個 page 幾小時」），迴圈模型適合算自己的真實工時。**兩個都算，收斂在 ±15% 內才可信**；若法 A 明顯高於迴圈模型，差額通常就是「把 AI 已經能做的事按人工計價」。

### Step 4 — 卡關桶要標註「事實 vs 推論」，然後去查證

每一條卡關項都要標明它是**查證過的事實**還是**推論的風險**。推論的項目要主動去 repo 驗證——這是估時最有價值的動作，因為：

- 查證後成立 → 這條變成不可爭辯的事實，別人質疑時你不用讓
- 查證後不成立 → 直接砍掉，數字自動變便宜

**AI 時代的典型卡關項**（都要逐條查證是否適用）：

1. **AI 看不到渲染結果的東西** — 多欄 sticky 的像素位移、複雜 CSS layout、動畫。必然 2–3 輪。
2. **無型別安全網的 debug** — prop 傳錯 → 畫面空白、無 stack trace。對策：先讓 AI 寫測試再寫實作，測試在此扮演型別系統的角色。
3. **改造既有的狀態機** — 特別是用複合鍵、跨頁狀態同步的。標註「唯讀，只能擴充不能重寫」。
   ⚠️ **先過 Step 3 的 additive 判準**：若只是「在既有分歧點加一個獨立分支、既有分支行為不變」，這條不成立，不要計價。
4. **兩階段提交 / dirty state** — 跨彈窗暫存、離頁攔截、送出後清空。AI 很少一次到位。
5. **動態增刪列** — 邊界與驗證。
6. **專案自訂慣例** — 例如成功判定不是 HTTP status 而是 `res.code === "P009"`。不講清楚 AI 會產通用 `try/catch`，全數要重改。

### Step 5 — 四法交叉驗證

單一算法會系統性偏誤（尤其模組拆解會每項往上湊）。至少算兩種：

- **法 A：畫面單位 × 實測速度 + 非建置成本** ← 對外報價與跨人對帳用，別人聽得懂
- **法 B：驗證點數量** — Σ(表格 × 狀態數) + Σ(彈窗 × 狀態數) + Σ(API × 回應數)，每點 3–4 分鐘 × 輪數
- **法 C：Review 行數** — 機械碼 @ 800 行/hr + 邏輯碼 @ 250 行/hr（無 TypeScript 時用 250；有 TS 可到 400）
- **法 D：迴圈數**（Step 3.5）— D×4min + J×20min + 純人類工時 ← **算自己真實工時最準**

四法應收斂在 ±15% 內。若某法明顯偏離，去找原因——通常是漏了一整桶。
**法 A 高於法 D 超過 30% 時，差額幾乎都是「把 AI 已經能做的事按人工計價」**，不是法 D 太樂觀。

### Step 5.5 — **工時與工期分開報**（否則一定被指為「buffer 太扯」）

被質疑估太多，八成不是因為某一桶算貴，而是因為把**兩種完全不同的東西加在同一個數字裡**：

| | 定義 | 誰能壓縮 | 例 |
|---|---|---|---|
| **工時（effort）** | 你實際動手的時間 | **你**（AI 讓這桶大幅縮小） | 建置、review、串 API、修正、回歸、發版 |
| **工期（calendar）** | 等別人的時間 | **不是你** | PM 點頁面、UAT 回饋輪次、後端交付 API、Figma 取得權限 |

**報價格式必須拆成兩行：**

> 我的工時 **X hr**；另有 **Y hr 是等他人回應的工期**（UAT 幾輪、PM 何時能點、API 何時到）。
> 工時我背，工期取決於對方節奏。

為什麼一定要拆：
- 對方聽到「30 hr」會用自己的開發速度去對照，發現差 3 倍就認定你在報 buffer。
- 拆開後他看到「我的工時 12 hr，UAT 等你 6 hr」，爭論會自動轉向「那 UAT 要幾輪」—— **這才是可以談出結論的問題。**
- 工期塞在工時裡，還會讓你自己失去壓縮工時的動力（反正總數看起來很大）。

### Step 5.6 — **報淨值，不抓 buffer**（KuanLin 2026-08 明確指定）

> 「我們一天開發 6 hr（已含 buffer），請你完全不用再次抓 buffer。」

**預設政策：估時報淨工時，buffer 由需求方在日容量裡自己吸收。** 不要加百分比加成、不要「以防萬一」、不要把同一個風險在兩桶各算一次。

**取代 buffer 的機制是「破了會漲的具名前提」**（Step 6）：

| ❌ 抓 buffer | ✅ 報淨值 + 具名前提 |
|---|---|
| 「SSO 那格算 12.5 hr，因為改別人系統有風險」 | 「SSO 4.3 hr。**若那支既有 API 的欄位是多處組裝 → 5.0；若優先序必須做在 SSO 而非 consumer → 7.5。**這兩條破了直接延，我不吸收」 |

差別在於：buffer 是我替對方決定要留多少餘裕；具名前提是**把風險連同觸發條件交還給對方**，他可以自己決定要不要留、留多少。

**這個政策下，估時者要主動說出兩句話：**
1. 「這個數字是淨值，沒有 buffer。」
2. 「以下 N 條破了我不吸收，直接延期。」

**自我檢查：把每一項的依據唸出來。** 唸不出「這 X hr 是為了哪一個查證過的具名項目」就是空氣，砍掉。
2026-08 實測拔掉的三種空氣：
- 校準數字沒按量體外推（「無 TS 靜默失敗 3 次」是 7,266 行/12 單位的實測，套到 2,500 行/6 單位應該是 1.5 次）
- 「勘查既有邏輯」給了 4 個 J 迴圈，實際是「grep 一個欄位名 + 讀一支 serializer」= 1 個 J
- 對版給 1.5 hr，但根本沒有 Figma，視覺真相就是手上那份 HTML → 1.0

### Step 5.7 — **算出地板，並說出「剩下多少才是真的在寫東西」**

報完總數要主動拆出**不可壓縮的部分**。沒有這一段，對方只會說「再想辦法壓一點」，而他不知道該壓哪裡。

**三類不可壓縮項**：

| 類別 | 內容 | 為什麼壓不了 |
|---|---|---|
| 他人時間 | UAT 輪次、跨團隊聯調、PM 點頁面 | 與你的開發速度無關 |
| Review | 依 Step 6 前提 1 選定的檔次 | 這是**前提的內容**，要壓就是改前提，不是改估時 |
| 發版 pipeline | **每個系統一條，不可合併** | 打包／上正式機／各自的流程 |

**輸出格式：**

> 32.5 hr 裡有 **18 hr 我壓不了**（UAT + 聯調 9.5、review 5.5、四條發版 pipeline 3.0）= **55%**。
> **剩下 14.5 hr 才是真的在寫東西。** 想低於 30 hr，要動的是前提（review 降檔／UAT 一輪／砍掉一個系統），不是再擠估時。

這段話把對話從「你估太多」轉成「我們要不要改前提」—— **和 Step 6 是同一個目的，但它是從成本結構切入，對方更難反駁。**

#### 多系統需求：成本在邊界，不在功能

四系統的需求不是「四個小需求相加」。單看每個系統都只有 3~16 hr，但**邊界成本是額外的**：

- 同一份 API 契約要對 N 方定案（每多一方，前置桶就多一輪來回）
- **N 條獨立發版 pipeline**，不可合併（這是地板的第三類）
- 一個語意（例如 fail-open、逾時、錯誤碼）要在 N 層各實作一次且保持一致
- 跨系統聯調的排程本身就是工期

> **但要防反向錯誤**：邊界成本不等於「每個系統都按改造既有計價」。先用 Step 3 的 additive 判準逐系統分類，再加邊界成本。2026-08 實測就是這裡出錯 —— 把四個系統都當改造，多算了 30 hr。

### Step 6 — 報「綁前提的數字」，不報單一數字

**這是最重要的一步。** 單一數字必然會被吵；綁前提的數字把爭論從「你估太多」轉成「那我們要不要達成這個前提」。

格式：

> **前提全成立 → N 小時 / D 個工作日，我背這個數字。**
> ① <最可能破的前提>
> ② <驗收標準前提>
> ③ <外部依賴前提>
> **任一條破 → M 小時 / D' 天，自動延期，不用回頭重談。**

必問的四個前提（**第 1 條是新加的，而且它最貴**）：

#### 1. Review 深度 —— 值 3 ~ 25 hr，比其他任何前提都貴

7,000 行 AI 產出的程式碼，merge 前人類要讀到多深？**三檔定價**（以 ~7,000 行 production 為基準，行數近似線性）：

| 檔次 | 內容 | hr | 適用 |
|---|---|---|---|
| **A. 抽查** | 只讀「會算錯錢」的模組（金額/費率/門檻判斷）+ 共用契約 | **3** | 內部工具、mock 階段、錯了無財務後果 |
| **B. 區塊概念 + 架構** ★ | 讀架構與資料流；每支檔案理解「它做什麼、介面是什麼、依賴誰」；金額邏輯逐行讀 | **8** | **多數情況的正解**（KuanLin 2026-08 指定的預設檔次） |
| **C. 逐行** | 全量逐行（機械碼 800 行/hr + 邏輯碼 250 行/hr） | **25** | 法遵稽核要求、對外金流 |

> 這一條原本被隱含在「法 C：Review 行數」裡而沒有浮上檯面，導致估時無法討論。**它必須是一個明問的前提。**
> 檔次 B 不是「打折的 C」—— 它換掉的是**驗證機制**：由測試 + 程式化量測（截圖斷言、位移量測、跨寬度溢出檢查）承接「程式碼有沒有做對」，人類負責「架構有沒有做對」。
> 報價時要一起講清楚**替代的驗證機制**，否則對方會以為你在省工。

#### 2. 後端 API 是否完整可串（不是「規劃中」）
最常破的一條。主機檔轉出（SERP*/CSMD* 之類）的欄位命名常與規格書不同，格式往往要等實際跑檔才知道 → mock 可能要重做。

#### 3. 驗收標準：功能對即可，還是要逐像素對版？
「不求完美」這四個字值 5.5 hr。另外先確認 **Figma 拿不拿得到** —— 需登入而拿不到的話，對版工時無論如何都下不去。

#### 4. UAT 幾輪
除非明文約定，預設兩輪。這是他人的時間，與開發速度無關。

#### 5.（若適用）RWD 做到哪一層
平板可用 vs 手機可用是兩個量級。見 Step 1。

## 兩個估時對不上時：用「對帳表」收斂

當你的數字跟別人差很多（例如 78 vs 50），**不要爭總量，拆桶對帳**。

| 階段 | 對方 | 我 | 差 |
|---|---|---|---|
| 理解需求 | 7 | 6 | ~0 |
| **建置** | **7** | **36** | **−29** |
| API 整合 | 7 | 5 | ~0 |
| Debug | 21 | 21.5 | ~0 |
| Buffer | 7 | 10 | −3 |

實測經驗：**差距幾乎總是集中在一格。** 找出那一格，然後問三個問題：

1. **桶子邊界畫在哪？** 對方說「UI 一天出來 8 成」——**8 成**。剩下 2 成他放進了 debug 桶。你放進了建置桶。這是 accounting 差異不是判斷差異。
2. **畫面單位數一樣嗎？** 他數 6 頁，你數 12 個畫面單位。
3. **前提一樣嗎？** 他假設「不求完美 + API 完整」，你假設「求對版 + API 待定」。**把前提對齊後，兩個數字通常會收斂到 ±15%。**

> 對帳的價值：三格獨立算出同樣數字，代表那三格是**穩的**；把爭論收斂到單一格，才可能真的談出結論。

## AI 加速不了的事（地板的**成因**）

> 這一節解釋「為什麼有地板」；**地板的算法與輸出格式在 Step 5.7**。兩節要一起用：先用這裡判斷哪些項目屬於地板，再用 Step 5.7 算佔比並報出來。

寫進估時文件裡，這是回答「為什麼還要這麼久」的標準答案。**2026-08 實測後，其中兩條要修正：**

1. **他人的時間**（桶 ⑤）— PM 點頁面、列問題、你修、他再點。與你的開發速度無關。**這條最硬，完全不可壓縮。**
2. **架構判斷**（桶 ⑥）— 「這個抽象切對了嗎、契約會不會讓五個 agent 各寫一套」只有人能判斷。可以不逐行讀，但不能不看架構。
3. **視覺回饋迴圈**（桶 ④）— ⚠️ **部分可自動化了。** AI 仍看不到渲染結果，但可以**程式化量測**：`boundingBox` 量凍結欄位移、`scrollWidth > innerWidth` 抓橫向溢出、斷言內容非空。
   → **仍需人眼的只剩「美感與一致性」**（間距、語氣、視覺層級），可量測的部分（位移、溢出、有沒有東西）應該寫成腳本。
   → 但要小心：**不能失敗的驗證不算驗證**。實測踩過 —— 截圖腳本只檢查「點得到 tab」，結果對 8 個空白頁面全回報 OK。腳本必須有內容斷言。
4. **決策而非產出**（桶 ①）— ⚠️ **視 demo 形態可能歸零。** 若 prototype 內嵌原始碼，「上百處顯示決策」就直接有答案了（見 Step 0）。只有在 demo 是 bundle 或截圖時這條才成立。
5. **驗證輪次**（桶 ③）— AI 每次修正仍要重新確認，但「確認」可以是跑腳本而非人眼。輪次不歸零，單輪成本大幅下降。

**修正後的地板推論**：即使建置歸零，案子仍需原估的 **40%（review 檔次 A/B + 前提都成立）到 105%（檔次 C + 前提破）**。<br>
判斷估時是否過於樂觀的最快檢查已經不是「建置佔比」，而是：**④⑤⑥ 三桶有沒有被獨立計價、有沒有綁前提。**

### 建置佔比的參考值

> ⚠️ **舊表是「人類逐行 review」前提下的數字，已被 2026-08 實測推翻。** 建置佔比取決於 review 檔次：

| review 檔次 | 建置佔比 | 說明 |
|---|---|---|
| C 逐行 | ~45%（金融 CMS） | 舊表的世界。review 與建置同量級，兩者一起主導總價 |
| **B 區塊 + 架構** ★ | **~6–7%** | Lend Zone：建置 1.75 hr / 總 30 hr。新手測驗（四系統）：D 迴圈 34×4min = 2.3 hr / 總 32.5 hr = **7%**。**兩案獨立收斂到同一比例** |
| A 抽查 | ~7% | 建置 1.75 hr / 總 25 hr |

**所以「這個案子多大」已經不是主要問題。** 實測 production 行數可以預測得很準（+13%），但工時差 27 倍。**改成先問 review 檔次與 ④⑤ 的前提。**

### 全 AI 開發、人工輔助 —— 這是預設模式，不是特例

KuanLin 2026-08 明確表示：團隊之後**全部**採「全 AI 開發、人工輔助」。所以估時預設就套這個模式，不需要每次都問要不要用 AI。這個模式下：

- 桶② 用迴圈計價(Step 3.5),**不要用人類工時估桶②**;報淨值,工作日 = 淨工時 ÷ 6(Step 5.6)
- 人類的角色是：Step 0.5 的提問、Step 0/1 的勘查、規格轉譯的**決策**（不是產出）、派工、**架構 review**、對版、UAT 對應
- **平行 agent 的上限不是「人類 review queue」** —— 實測 5 個並行沒有塞車，因為 review 已改由測試與量測承接。
  真正的塞車點是**共寫點衝突**：兩個 agent 對同一支 endpoint 各自發明註冊機制而互相覆蓋，把 build 弄壞。
  → **派工時「唯一共寫點」不只要標出來，必須連機制一起指定**（例：「共用 endpoint 的分派器由主 session 建立在 X 檔，你只匯出資料並呼叫 registerXxx」）。不指定機制等於邀請每個人各寫一套。
- 估時要**額外計入驗證基礎設施的固定成本**（不隨程式碼量變動）：登入閘門的繞道、截圖/量測腳本、跨寬度檢查 —— 中型案約 **1–2 hr**，但它是讓 review 從 25 hr 降到 8 hr 的前提。

## 常見估時錯誤（自我檢查清單）

**前七項是 2026-08 兩次實測後補的，優先檢查（1–3 是新手測驗案的，4–7 是Lend Zone 案的）：**

- [ ] **把 additive 當真改造計價** → **本清單第一位。** 判準是「舊 client 打同一支 API 行為會不會變」，不是「有沒有動到別人的系統」。誤判一格 = 8 hr 空氣，四格 = 30 hr
- [ ] **沒問「這件事現在是怎麼做的」**（Step 0.5）→ 一個既有欄位名（`can_online_happy_call`）值 15~20 hr。**比驗 demo 形態更高投報率**
- [ ] **校準數字沒按量體外推** → 「無 TS 靜默失敗 3 次」是 7,266 行/12 單位的實測。套到 2,500 行/6 單位要按比例縮到 1.5 次。**照抄校準數字就是抓 buffer**
- [ ] **抓了 buffer** → 政策是報淨值（Step 5.6）。用「破了會漲的具名前提」取代，並主動說「這是淨值」
- [ ] **沒先驗 demo 的原始碼形態**（Step 0）→ 可能白算 6 hr 的規格轉譯，並多背一條不存在的風險
- [ ] **只用小時估、沒算迴圈**（Step 3.5）→ 派工型與判斷型差 5 倍人類成本，均一價會高估
- [ ] **沒算地板、沒說「剩多少才是真的在寫東西」**（Step 5.7）→ 對方只會說「再壓一點」，而他不知道該壓哪
- [ ] **沒把 review 深度當成明問的前提** → 這一條值 3~25 hr，比 API 完整度更貴。隱含在「法 C」裡等於沒問。
- [ ] **還在用「建置佔 45%」的舊錨** → 在 review 檔次 B 之下建置只佔 ~6%。用舊錨會系統性高估 3–4 倍。
- [ ] **報 review 折扣時沒說替代的驗證機制** → 對方會以為你在省工。要一起講「測試 + 程式化量測承接程式碼正確性，人類負責架構」。
- [ ] **均一價**：所有畫面都抓一樣的時數 → 一定高估簡單頁、低估複雜頁
- [ ] **數頁面而非畫面單位** → 系統性低估（最常見的低估原因）
- [ ] **沒設驗收前提** → 對方假設「不求完美」，你算了對版工，數字對不上
- [ ] **忘記問 RWD** → 「repo 沒 media query」是現狀不是需求，一定要問；且平板/手機是兩個量級
- [ ] **假設「UI lib 應該都有」** → 一定要 grep 驗證。8 成猜對，剩 2 成是真成本
- [ ] **把真改造當新建打折** → 真改造更貴。但**反向錯誤（把 additive 當改造）更常犯也更貴**，見第 1 項
- [ ] **只用一種算法** → 模組拆解會每項往上湊
- [ ] **卡關項沒標「事實/推論」** → 被質疑時無法防守
- [ ] **報單一數字** → 必然被吵
- [ ] **忘記測試是固定成本** → 但範圍可談：只測邏輯與關鍵互動 vs 每個 component 一支，差 3 倍（實測 1,176 行 vs 預估 3,500 行）
- [ ] **UAT 只算一輪** → 除非明文約定，預設兩輪
- [ ] **忘記算驗證基礎設施** → 登入繞道、截圖/量測腳本，中型案 1–2 hr 固定成本
- [ ] **派工只標共寫點卻不指定機制** → 多個 agent 會各自發明一套並互相覆蓋

## 輸出格式

估時文件應含（可交第三方審查）：

1. 範圍界定 —— **明確列出排除項**（避免對方拿範圍外的工作質疑數字）
2. 可驗證事實勘查（附 `檔案:行號`），含 **Step 0.5 問到的既有 flag／欄位／API**
3. 前提條件
4. **逐系統 additive／真改造 分類表**（多系統需求必附，這是最大的單一價差）
5. 逐項估時表：**D／J 迴圈數 + 迴圈人類工時 + 純人類工時 + 我的工時 + 等他人 + capacity**，每項標註依據，卡關項標「事實/推論」
6. **地板分析**：不可壓縮項與佔比 +「剩下多少才是真的在寫東西」（Step 5.7）
7. **淨值宣告**：「這是淨值，沒有 buffer」＋「以下 N 條破了不吸收，直接延期」
8. 壓縮方案階梯（N → N−x → N−y，各自說明砍掉什麼——且說明砍的是**前提**還是**範圍**）
9. 風險與阻擋項
10. **請審查者具體回答的封閉式問題**（含「你認為正確的數字是多少」——逼對方出數字才會逼他去算）

若估時經過修正，**把修正歷程與原因寫進文件**，每一版標明「數字 / 變動原因 / 方向」。兩種病徵要自己抓出來：

| 病徵 | 診斷 | 處置 |
|---|---|---|
| **多次修正都在同一數字附近打轉** | 錨定偏誤，在護盤 | 對方有立場質疑，重算 |
| **連續多次單向修正（尤其一路下滑）** | **有一個沒被命名的系統性偏誤**，正在被逐次擠出來 | **停下來命名它**，不要繼續一次一次滑 |

第二種比第一種危險，因為它看起來像「在收斂」。2026-08 新手測驗案四版 62.5 → 54 → 43 → 32.5 全部往下，根因只有一個：**只要動到別人的系統就套改造既有溢價**。命名之後才知道要一次修完，而不是等對方每次質疑一格就讓一格。

**單向修正時的自我防護**：主動標出**唯一往上的那一格**及其理由。若連一格都往上不了，就是還沒找到根因 —— 那份估時不該定稿。
